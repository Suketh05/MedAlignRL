# NOTE: sglang, jsonschema, and bitsandbytes are deliberately left out of this
# file. sglang (and jsonschema, which it needs) are only used by agents.py,
# which never runs in Colab -- that script runs on your local machine against
# the merged model, per the split-workflow design. bitsandbytes was in the
# original requirements.txt for 4-bit loading but nothing in this codebase
# actually wires that up, so it's dead weight either way. Same story for
# pandas and pyyaml, also dropped here -- nothing in src/ imports either one.
# Installing sglang's full dependency tree in every Colab notebook for a
# script that never runs there was the single biggest thing slowing down
# every setup cell.
#
# torch is deliberately left out too, unlike in requirements.txt. Notebook
# setup cells install with `pip install -U`, and torch>=2.2.0 is loose enough
# that -U would fetch a newer torch than Colab's preinstalled build without
# touching torchvision (not a dependency of this project, but still present
# and imported transitively via transformers/peft). That version split breaks
# torchvision's compiled ops against the new torch ("operator torchvision::nms
# does not exist"), which then breaks the transformers/peft import chain
# entirely. Colab's preinstalled torch is already CUDA-matched to the VM and
# always satisfies >=2.2.0, so just leave it alone here.
#
# transformers, peft, trl, and accelerate are pinned to exact versions
# (verified working together) instead of floors. Colab's base image ships
# pre-release builds of trl/transformers with version numbers HIGHER than
# anything ever published to PyPI (e.g. trl reporting 1.10.0 when 0.24.0 is
# the actual latest PyPI release) specifically so plain `pip install -U`
# never replaces them -- -U only installs a version newer than what's
# already there, and nothing on PyPI outranks Colab's inflated preinstalled
# version. That stale build's DPOConfig doesn't accept max_prompt_length as
# a keyword arg, breaking train_dpo.py. An exact `==` pin forces pip to
# install that specific version regardless of whether the installed one
# looks newer by version number, which floors can't do.
#
# scispacy is deliberately NOT listed either, same reasoning as
# requirements.txt: reward.py only ever does spacy.load("en_core_sci_sm"),
# never `import scispacy`, and that model's own metadata depends on plain
# spacy, not the scispacy package. scispacy's PyPI metadata pins numpy<2.0,
# and under `pip install -U` that downgrades numpy out from under every
# other compiled package already linked against numpy 2.x's ABI in Colab's
# environment -- "numpy.dtype size changed, may indicate binary
# incompatibility" at import time, even in notebooks that never touch
# scispacy at all (this setup cell is shared across all 7).
#
# spacy is pinned exactly (like transformers/peft/trl/accelerate above),
# not just uncapped, and to a version ABOVE what en_core_sci_sm declares
# support for (<3.8.0): a floor alone (spacy>=3.7.4) still resolved to
# Colab's already-installed 3.7.5 (kept around because Colab's own fastai
# depends on it) even under `pip install -U` -- pip is allowed to satisfy a
# floor with whatever's already present rather than the newest release.
# That kept thinc on the 8.2.x line, which caps numpy<2.0, reproducing the
# same "numpy.dtype size changed" ABI breakage scispacy caused, just one
# dependency hop over (spacy<3.8 -> thinc<8.3 -> numpy<2.0) and inside
# thinc's own compiled extension this time. An exact pin forces pip to
# install that specific version regardless of what's already satisfying
# the floor, same fix as the trl ghost-version issue above.
#
# AllenAI has never shipped an en_core_sci_sm build newer than 0.5.4
# (spacy 3.7-era), so there's no newer-model escape hatch -- the model is
# installed with --no-deps in notebook 01 so it can't force spacy back
# down to satisfy its own declared cap. spaCy's model serialization format
# has stayed stable across the 3.x line, so loading a 3.7-packaged model
# under 3.8 should just emit an advisory warning; reward.py's NER loader
# catches any load failure (not just "model missing") and falls back to
# en_core_web_sm as a safety net if that assumption is ever wrong.
#
# Use requirements.txt (the full one) only on your local machine, when you're
# actually running agents.py against the served model.
